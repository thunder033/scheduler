## General Coding Conventions

- Use named constants for literal string and numeric values; avoid magic numbers/values
  - Check for existing potential relevant constants when writing new code

## Development Flow

- NEVER use git stash or other commands that touch the index without asking.
- When using the Bash tool, ALWAYS give an explanation before the tool call of what will be done
- When given instructions to write code, only write was explicitly asked. Wait for review and further instructions before proceeding.
- Prefer Read/Write tools over Bash unless there is a specific reason for Bash
- Don't attempt to validate the functionality in the browser after edits, the dev will manually validate functionality in the browser
- Use the ts-quality skill to check code quality after edits
- Use `--no-tui` with NX commands
- The project uses npx/npm; ignore recommendations to use PNPM

## Type Conventions

- Prefer `interface` for object shapes that will be extended
- Use `type` for unions, intersections, mapped types
- Never use `any` — use `unknown` and narrow, or `never` for exhaustive checks
- Export types alongside implementations, not in separate files

## Test Conventions

- Each TypeScript file in `src` has a corresponding test file; exceptions are:
  - test files (`.spec.ts`) or test support files (`.harness.ts`, `.test-utils.ts`, or under `test-utils/`)
  - files with no logic that only list values, other config, or exports (i.e. constants)
- Use factory functions to generate test data instead of raw object definitions, especially for large and/or repeated structures
  - For `User`, `Timeslot` and `Appointment`, use the shared mock factories (see Test Data), not spec-local factories or literals
- Tests use a common, parameterized `setup` method for preparing each scenario and avoid beforeEach hooks
  - the setup method usually returns an object with test fixtures and data to use in the scenario
- Name test scenarios as concise declarations of the behavior, in the present tense, without "should": `orders each section from available to unavailable`, `does not offer editing to a member`, `is expanded by default`
- Tests focus on the behavior of the module under test
  - Focus on asserting how the module responds to interactions with its public interface
  - Avoid asserting against hard-coded properties or values, or static text
- Tests drive behavior through harnesses, not screen or fireEvent. screen is only for the test scene itself, such as an "outside" button or a test-only state reader.

## Test Data (scheduler-ui)

Mock and seed data come from `@org/scheduler-ui/data/testing` (`packages/scheduler-ui/data/src/testing.ts`), never from the main `@org/scheduler-ui/data` entry point.

- Each entity type has a lowercase factory that takes overrides: `mockUser`, `mockTimeslot`, `mockAppointment`
  - IDs are the entity name with a per-entity index (`user-1`, `timeslot-2`), generated by `nextMockId`; pass an `id` override only when the test needs a specific one
  - `mockTimeslotDraft` and `mockUserDraft` build the id-less payloads for creating an entity; they have no seeds
- Each factory carries named seed entities for the primary variants: `mockUser.COORDINATOR` / `.MEMBER` / `.PROSPECT`, `mockTimeslot.MONDAY_MORNING`, `mockAppointment.CONFIRMED`, etc.
  - Prefer a named seed over a factory call; call the factory with overrides only for a specific configuration (parameterized roles, multiple roles, a fixed id, a user distinct from the seeds)
  - When a variant is missing, add it as a named seed on the factory rather than a spec-local helper
  - Seeds are shared objects: never mutate them, and do not call `resetMockIds()` in specs that use them (new IDs would collide with the seeds')
- The stubbed services (`AuthService`, `UserService`, `TimeslotService`) start with the entities provided through the `SEED_USERS`, `SEED_TIMESLOTS`, `SEED_APPOINTMENTS` and `SEED_CURRENT_USER` tokens, which have no defaults
  - The app provides them with `provideSeedData()` from the testing entry point
  - Tests provide only the entities they expect: `provideTestState({ users, timeslots, appointments, currentUser })`, or `provideTestSeeds(...)` when not using the store; unspecified seeds are empty
  - Specs that don't use `provideTestState` (e.g. in `state`, which test-utils depends on) provide the tokens directly
- Tests declare the seeded entities they rely on in `setup` and assert against those entities (e.g. `seededUsers`), not against hard-coded names or ids

# General Guidelines for working with Nx

- For navigating/exploring the workspace, invoke the `nx-workspace` skill first - it has patterns for querying projects, targets, and dependencies
- When running tasks (for example build, lint, test, e2e, etc.), always prefer running the task through `nx` (i.e. `nx run`, `nx run-many`, `nx affected`) instead of using the underlying tooling directly
  - Nx hang: nx test hangs rarely, about 2% of runs, at vitest startup, before any test runs. It is not a test failure. Run Nx commands under perl -e 'alarm N; exec @ARGV' (macOS has no timeout).
  - use `nx format` instead of prettier directly
- Prefix nx commands with the NPX package manager
- You have access to the Nx MCP server and its tools, use them to help the user
- For Nx plugin best practices, check `node_modules/@nx/<plugin>/PLUGIN.md`. Not all plugins have this file - proceed without it if unavailable.
- NEVER guess CLI flags - always check nx_docs or `--help` first when unsure

## Scaffolding & Generators

- For scaffolding tasks (creating apps, libs, project structure, setup), ALWAYS invoke the `nx-generate` skill FIRST before exploring or calling MCP tools

## When to use nx_docs

- USE for: advanced config options, unfamiliar flags, migration guides, plugin configuration, edge cases
- DON'T USE for: basic generator syntax (`nx g @nx/react:app`), standard commands, things you already know
- The `nx-generate` skill handles generator discovery internally - don't call nx_docs just to look up generator syntax
